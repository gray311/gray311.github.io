手工 visual harness 的边界：VISTA 的消融与局限

October 27, 2026·vista·visual-harness·ablation·ai4harness

VISTA 是一层 人工设计 的视觉 harness：它不含模型调用循环，而是把环境包装成一组工具（inspect 返回裁剪图，read_pixels 返回符号网格），注册进一个现成的 coding agent（Codex CLI 或 Claude Code）。本文要回答的是：它的收益究竟来自哪一部分，以及手工设计这件事本身在哪里触到天花板。

TL;DR
  • 增益来自两个工具的协同，而非任何单个部件。只给 inspect = 48.7%，与完全不给工具相同；只给 read_pixels = 43.6%，比不给还低。两个一起给 = 61.5%。
  • 「只靠文字更新信息」行不通。read_pixels 返回的就是纯文本符号网格——单独使用时它是负收益。
  • Agentic loop 的边际收益极低。只允许 1 次工具调用已拿到 53.8%；完整 VISTA 中位调用 27 次，只多换来 7.7 点。
  • Thinking flow 主要让 agent 看得更多，而非更准。去掉它掉 5.1 点，但中位工具调用从 27 降到 7。
  • 不存在单一最优配置。22 个子类上有 5 个不同最优，逐子类最优比 VISTA 的固定设置平均高 +52 点；4 个子类在固定设置下得分为 0。

1BabyVision 是什么

一个静态视觉问答 benchmark（UniPat-AI/BabyVision）， 不是游戏：388 道题，每题 = 一张图 + 一个问题 + 一个答案。没有环境、没有动作、没有回合。 名字来源于它的定位——这些题对幼儿很简单，对 MLLM 很难，考的是「看」本身，而非知识或推理深度。

答案两种格式：choice（135 题）与 blank（253 题）。 VISTA 论文只报告了 Maze(20) + Connect the lines(19) 这 39 题，占全集 10%——恰好是最接近 ARC 式连线追踪的两类。本文的 harness 级探针（§5）覆盖全部 22 个子类。

1.1 模型要做什么

官方的 plain implementation 极简——一次 API 调用：图像 + 问题 + "Think about the question and give your final answer in oxed{Answer} format."， 无 system prompt、无工具、无多轮。然后正则抽 oxed{...}，交给 LLM judge 判对错。

1.2 一条真实 trajectory

同一道题在完整 VISTA harness 下的全部工具调用（逐调用日志，未经编辑）：

turntool返回图数返回字符返回内容开头
1inspect51027{"current_state_unchanged":true,"view_count":5,"views":[{"event":0,"image_size":{"height…
2read_pixels01395{"color_bits":4,"current_state_unchanged":true,"palette":{"0":"#00AA99","1":"#00AAAA","2…
2read_pixels01310{"color_bits":4,"current_state_unchanged":true,"palette":{"0":"#11AA99","1":"#22AA88","2…

3 轮、3 次工具调用，最终输出 \boxed{\text{(B) Bottom-left entrance}}——答对。

这条轨迹恰好演示了 §3 要讲的协同机制：

  1. inspect 先定位：一次要了 5 个视图，把 600×600 的整图收窄到三个入口与出口附近。
  2. read_pixels 再判定：在那些小区域上读精确颜色。返回的调色板是 #00AA99、#11AA99、#22AA88……全是青绿色系的细微差别， 即迷宫墙体渐变的局部取值，用来判断两段墙是否属于同一条连通路径。
  3. 两次 read_pixels 在同一轮发出，并行比较两个区域。
如果没有 inspect 先收窄，read_pixels 对整图会读出 754 种颜色、直接撞上 64 符号墙。 而在被选中的小区域里颜色数降到个位数，工具才可用。

同时它也暴露了 harness 的代价：返回给模型的是 1000–1400 字符的 JSON metadata，真正的信息淹没在结构里； 答一道选择题花了 129 秒。而这还是顺利的一条——完整 VISTA 的中位是 15 轮、27 次工具调用， 且 39 题里有 17 题撞满轮次上限，那些题的正确率只有 25%，而像这条一样自行收敛的题正确率是 83–87%。

2测量平台

全部实验在 BabyVision 上进行，用 VISTA 自己的代码（数据集、官方问题格式、system prompt、工具 schema、TaskContext 这个 harness 本体、以及 exact_match 打分）。只替换执行器：官方的 Codex-CLI-in-Docker 在本机无法运行（无 Docker、codex-cli 版本不符且未登录），改为直接的 tool-calling 循环驱动 gpt-5.6-sol。

BabyVision 不是 game task，这一点对本文结论很重要：它是静态视觉问答，22 个子类涵盖 3D 视图、找影子、计数、折纸、图案补全、迷宫、连线。下面关于非游戏域的结论都建立在这些真实数据上。

3消融：拆开那 12.8 点

整个 harness 增益落在「有没有工具」这一步：同等推理预算下，只给 VISTA 的 prompt 而不给工具 = 48.7%，与原生实现完全相同——prompt 本身贡献为零。下面每个 arm 都只相对完整 VISTA 改动一处。

逐条回答

① Visual frame memory —— 7.7 点，不是主因。把保留的裁剪图清零（看过即丢）仍有 53.8%。VISTA 主打的 “lossless visual memory” 在这里远没有宣传的关键。

② Agentic loop —— 7.7 点，边际收益极低。single_step 只允许 1 次工具调用就必须作答，仍有 53.8%，已比无工具高 5.1 点。完整 VISTA 中位调用 27 次，只再多换 7.7 点。

③ Tools —— 最反直觉的一条。单独给 inspect 等于没给（48.7% = 48.7%）；单独给 read_pixels 比没给还差（43.6%）。两个一起 = 61.5%。增益是协同效应，不属于任何单个工具。

④ Thinking flow —— 5.1 点，但代价是 4 倍的观察量。去掉 observe→state-what-changed 的文本后掉到 56.4%，而中位工具调用从 27 降到 7。那段 prompt 主要作用是让 agent 看得更多，而非看得更准。

⑤ 只靠文字能否达到同样效果 —— 不能，而且更糟。这个问题不需要另造系统：read_pixels 返回的就是纯文本符号网格，从不返回图像。readpixels_only = 43.6%，比完全没有工具低 5.1 点。给模型一堆它用不好的数字，比什么都不给更有害。

4为什么两个工具必须合起来才有用

两个工具的能力互补，而且各自残缺：

inspectread_pixels
返回裁剪图（NEAREST 放大）符号网格 + 调色板（纯文本）
擅长定位：哪里有东西、整体走向判定：这两格是不是同一个颜色
盲区放大后仍靠目测，不引入模型自己做不到的新信息没有空间语义；超 64 色直接报错；每格只取中心单像素

所以：

  • inspect 单独 = 0 增益，因为它只是换了分辨率再看一眼——而模型本来就能看原图。
  • read_pixels 单独 = 负增益，因为它必须先知道该读哪个区域。盲读整图会撞上 64 符号墙（见 §5：64×64 网格下 63% 的图像直接报错），而中心像素采样会把 46% 含内容的格子报成空白。
inspect 把搜索空间收窄到一个小区域，于是 read_pixels 在那个区域上颜色数远少于 64、特征相对格子足够大。即 inspect 把 read_pixels 从「不可用」变成「可用」。这就是 0 + (−5) = +12.8 的来源。
这条机制仍在直接验证中

上面的解释来自代码结构与 §5 的 harness 级测量。一个带逐调用日志的实验正在运行，用于直接检验其预测：readpixels_only 中 read_pixels 的失败率应显著高于完整 VISTA 中的。结果会补入本节。

5跳出 game task：原语是按 ARC 的世界长的

ARC-AGI-3 的视觉世界有四个性质，VISTA 把它们当成了普适前提：

ARC 的性质VISTA 的设计选择出了 ARC 就失效
离散的 16 色调色板精确色值 + 64 符号表自然图像 / 抗锯齿一律爆表
每格一个平坦色块每格取中心单像素，从不平均细线 / 纹理被漏采
64×64 的小网格帧全量归档、无损记忆高分辨率 / 长文档 / 视频撑爆预算
离散回合 + 可编号帧turn/frame 寻址静态图、文档、流式视频没有「回合」

规律很清楚：越接近 ARC 的「平面色块」越能用，越接近真实渲染（阴影、渐变、抗锯齿）越是全军覆没。3D 渲染类 12/12 全败——而这类图像恰是真实世界视觉任务的常态。

值得注意的是，VISTA 自己知道这个问题：core/support.py:46 的注释写着 “on a compressed or anti-aliased image every sample is its own color and a symbol table fills in one call”，于是手工加了 4-bit 量化这条旁路。它把失败率从 97% 压到 63%，但没有修好。

5.2 缺的不是参数，是原语

这比参数问题更根本。VISTA 只有两种视觉动作：裁剪放大与读像素。跳出游戏看，不同域需要的根本不是同一类原语：

域真正需要的原语VISTA 有吗
文档 / 表格 / 图表OCR、版面结构、表格抽取❌ 只能读像素
自然照片检测、分割、深度❌
科学影像（医学 / 卫星 / 显微）窗宽窗位、通道分离、测量标定❌
GUI agent元素树、可点击区域❌
3D / 多视角换视角、切片❌ 只能在固定 2D 图上裁剪
视频时间采样、关键帧、运动❌ frame 索引假设离散回合

读像素对一张财报表格毫无意义，对一张 CT 片同样毫无意义。而 VISTA 的 harness spec 里没有「换一种视觉原语」这件事——它只能调裁剪框和采样密度。

5.3 有「看」的原语，没有「找」的原语

inspect 要求 agent 先给出坐标，这隐含假设 agent 已经知道该看哪里。ARC 的 64×64 网格可以全扫，假设成立；但对一张 4K 截图、一页 PDF、一张卫星影像，「该看哪里」本身就是主要难题。VISTA 没有任何检索 / 显著性 / 搜索原语——这正是 read_pixels 单独使用时变成负收益的原因。

5.4 没有收敛机制，长程任务会发散

复现时量到：14/39 题在每次 pass 都不收敛（中位 27 次工具调用），而把轮次上限从 30 放宽到 80 掉 12.8 点。游戏任务有外部信号（分数、关卡、game over）帮助收敛；非游戏的视觉任务没有这种信号——没人告诉 agent「你已经看够了」。而停止策略完全不在 VISTA 的 harness spec 里，被外包给了 Codex CLI。

5.5 不存在单一最优配置

22 个子类上出现 5 个不同的最优配置，逐子类最优比 VISTA 的固定设置平均高 +52 点；4 个子类在固定设置下得分为 0（读取永远报错）。手工设计只能选一个点，而这个点对多数任务是次优甚至不可用的。

这个扫描的代理指标有偏

该目标奖励「合法 + ink recall」，因而偏向粗量化：3-bit 几乎通吃，因为颜色少才装得进 64 符号表。它没有惩罚丢失颜色区分度，而那会伤害 Pattern and Color Completion 这类任务。真正的 harness 演化奖励必须带一个颜色区分项——这本身也是一条设计教训。

6四类 limitation，对应四种演化空间

#问题性质能被 AI 演化吗
1量化 / 采样 / 网格等常量按 ARC 的色彩统计调死参数✅ 直接搜索，已验证 +52 点空间
2溢出就报错而不降级；中心单像素采样丢掉 46% 的证据策略✅ 策略选择（降级 / 合并 / 换算子）

第 3 点是跳出游戏后最关键的。前两类是「把旋钮调对」，第三类是「换一套旋钮」——不同视觉域需要的原语根本不同，人不可能为每个域手工设计一套 harness。

手工调参的实证：三次尝试，一正两负

复现过程中我按人的直觉改了三处，结果正好说明手工设计的困难：

改动效果
上下文预算：按轮次计 → 按图像数计+5.1
裁剪图挂到 tool 结果（贴近官方 MCP 形态）0（假设证伪）
轮次上限 30 → 80（VISTA 官方不限轮次）−12.8

唯一有效的改动是一个纯 harness 参数；放宽停止预算主动有害。这说明这些维度非单调、有最优点——适合搜索，而人手调不出来。

7对项目的意义

消融给出的核心事实是：VISTA 的 +12.8 不来自任何单一设计，而来自若干互相耦合的参数恰好配合得当。其中至少两个（上下文预算、停止策略）VISTA 根本没当作参数，另外两个（工具组合、读取配置）被固定成了对多数任务次优的单点。

这正是 AI4visual-harness 的立足点：这些参数非单调、相互耦合、且逐任务最优不同——人工设计必然停在局部最优。已经落地的第一步是把视觉参数提成可序列化的 VisualHarnessSpec（vista_probe/spec.py），默认值即 VISTA 的真实行为，于是每个变异都是对 baseline 的 diff。
