Design: how Lens evolves a visual harness

Motivation. A visual harness is task-specific. It covers the tools an agent uses to look at images, the instructions that make it use them, and when it looks. VISTA was hand-built for game screens, and off its home ground its tools go unused or break: read_pixels is 72% of VISTA's visual calls on ARC-AGI-3 but 0% on molecule renders, and it refuses on anti-aliased plots. Lens therefore searches for the visual harness per task family. A proposer model writes harness code, a frozen executor runs it, an evidence check asks whether the pictures did the work, and accepted harnesses go into a library that later tasks retrieve from. The full design document, with the literature, the taxonomy and the open questions, is at vista_probe/figures/lens_design.html.

"Called" is a diagnostic, never a reward; only "relied on" and "helped" can accept a visual harness. A harness with no visual use is judged on "helped" alone and reported as a non-visual gain.

What is evolved, and what is fixed

  • Evolved: the whole package. That is the system prompt, skills, custom tools as code, middlewares chosen and parameterised from a registry (budget and turn reminders, an automatic view after each evaluation, an automatic tool run before the first turn), the turn budget up to the seed's, and how many images stay in context.
  • Fixed: the executor model; the task's own interface (edit / evaluate / finish on discovery tasks, an answer in \boxed{} on BabyVision); the evaluator and scoring; and the turn cap, never above the seed's (36 on discovery tasks, 12 on BabyVision).
  • VISTA's tools: on discovery tasks they were offered as optional components, and no candidate ever took them. On BabyVision, VISTA's home benchmark, they are neither offered nor mentioned, so any image-reading tool is the proposer's own proposal.

Operator taxonomy

Prior knowledge for the Lens proposer. A vocabulary, not a template: the proposer writes harness code freely and may use none of this. It comes from the thinking-with-images literature (vista_probe/lens/taxonomy.json, built by vista_probe/lens/build_taxonomy.py). It holds 42 operations in 8 families, 13 task-property → operation priors, 8 principles and 26 pieces of negative evidence. It is shown to the proposer in every round as text (outer/propose.py: taxonomy_text). On BabyVision the 3 entries whose evidence comes from VISTA are hidden.

Principles

  • Score rosters, not operations. Giving a reasoner every tool scored below a random subset and below no tools at all (VisTA, ChartQA). Adding an operation can make a harness worse. (VisTA 2505.20289)
  • Synthesising a view from state pays far more than editing a given image. Rendering a graph, plot, board or next state produced the largest gains in the corpus; edits of a given image gave modest gains with regressions. Where the task lets the harness draw the view, what to draw is the main lever. (Visual Sketchpad 2406.09403; ViLaSR 2506.09965; VPRL 2505.11409; ReFocus 2501.05452)
  • Pay for corrections, not for calls. A fitness that rewards tool use gets theatre: a policy executes visual operations superficially while answering from text. Count instances a harness FIXES separately from instances it BREAKS; a break is worse than doing nothing. (Pixel Reasoner 2505.15966; VisTA 2505.20289 (+1 fix / -0.5 break))
  • Calling a tool is not relying on what it returned. Replacing every returned crop with a black image left V*Bench scores within 75.9-87.4% for all models: the tools were not doing the work. (VisualNeedle 2605.26380)
  • Use is sparse at the optimum. Trained tool policies converge to calling a tool on roughly one query in ten. Heavy use is not evidence of value; over-querying is a named failure phase. (OpenThinkIMG 2505.08617; DeepEyes 2505.14362)
  • Wording decides whether a tool is used. Models are reluctant to use novel visual operations; tool propensity differs by model. A capability the agent does not reach for is worth nothing, so the instruction that makes it reach is part of the harness. (Survey 2506.23918 §3.3.3; Visual Sketchpad (GPT-4 Turbo rarely segments); SoM)
  • A failed operation is not a no-op. After a tool error, models hallucinated content they never saw, or ignored the error and answered from text. An operation that errors on this task's views is harmful. (Pixel Reasoner 2505.15966)
  • The cheapest harness that suffices wins. The survey's blueprint routes simple tasks down a direct path and allows early exit; its worked example prefers a cheap measurement tool to a full simulation. (Survey 2506.23918 §2.2, §8.5.2)

* Thermoelastic's score is additive, 0.5·29.518/S + 0.5·44.758/T, so a design can drop the structural objective entirely and score on heat conduction alone. One of the 16 fresh evolved rollouts did: 5.557, with a structural term of 0.000. Without it the evolved harness is still 3.2× both baselines (p < 0.001). Photonics went from 1.37 to 5.758 in round 1, accepted nothing in round 2, and gained +0.004 in round 3 (in-loop). The round-3 gain held up on fresh rollouts: 5.763 against the round-1 incumbent's 5.755 (rank p < 0.001). Thermoelastic improved over two rounds (0.62 → 1.51 → 1.85 in-loop) and reached 2.15 on fresh rollouts. For reference, the best programs of the earlier GEPA ablation scored 5.768 (Photonics) and 1.586 (Thermoelastic). GEPA searched programs directly, about 22 evaluations per run, so these are reference points, not a controlled comparison.

beams2d is the counter-case, and the gate handled it. The text-only seed harness already averages 1.219, close to the best the GEPA ablation found (1.277). In three rounds the proposer wrote 12 candidates. None beat the seed harness on enough of the six selection seeds, so the gate accepted nothing. Fresh rollouts back the refusal: the best refused candidate scores 1.237 against the seed's 1.219, rank p = 0.118.

The proposer worked from the raw traces. On the six selection seeds, about 45% of the seed harness's evaluations were programs that crashed (41 of 92 on Photonics, 34 of 77 on Thermoelastic). It fixed that, not the pictures: it supplied a 93-line adjoint-FDFD optimiser as a skill on Photonics, and a construction template distilled from the best earlier rollouts on Thermoelastic. Photonics round 3 then found the next bottleneck: every evaluation restarted the optimiser from scratch. The proposer's fix was a tool of its own, continue_from_best, which writes the best design so far into the program as a warm start, so each evaluation continues the optimisation instead. The executor called it 9 times per rollout. So the loop invented a tool, but not a visual one.

2. VISTA's hand-designed visual harness does not transfer — on Photonics it is harmful

Rerunning VISTA with all of its visual output blanked (images and the pixel readout) raised its Photonics score from 0.97 to 1.88: blanking won on 11 of the 13 seeds that were not tied (rank p = 0.044). With real images the executor spent ~9 of its 36 turns on visual tools. VISTA's read_pixels hit its own limits six times: four refusals from its 64-symbol colour palette, which suits game screens but not anti-aliased plots, and two from its 4096-sample cap. Only 5 of 16 rollouts ever beat the starting program (13 of 16 when blanked). On Thermoelastic the images made no significant difference, and on beams2d the three arms are indistinguishable (seed 1.219, VISTA 1.217, VISTA blanked 1.218).

3. No evolved visual tool was shown to be load-bearing — and the evidence check is why we know

What this does and does not show

  • Shown: an RSI loop over HarnessTTT-format packages improves a frozen executor 3–6× on fresh rollouts. It invents task-specific tools as well as prompts and skills. A visual harness hand-built for games is neutral-to-harmful on discovery tasks. And a gain made by a visual harness is not evidence that its pictures did anything.
  • Not shown: a task where an evolved visual tool is load-bearing. On these tasks, with this executor, the bottlenecks were crashed solver code and restarted optimisation, and the proposer went after those. The open question is the one the design predicts: tasks where the state is hard to reason about except by looking.
  • The evolved harnesses carry task knowledge VISTA does not (an optimiser, a distilled construction, a warm-start tool). That is legitimate under HarnessTTT's framing, but it means "evolved vs VISTA" is not a test of visual design. The evidence check is what answers the visual question.
  • Thermoelastic's scoring has a loophole (the footnote under §1). VISTA (2 of 8) and the seed harness (1 of 8) also produced structure-free designs, at lower scores. The in-loop rollouts the gate accepted harnesses on were balanced designs, except one that scored only 0.23. But the task should score the two objectives jointly (their product, or the weaker of the two) before it goes in a paper.
  • Scale: three evolved tasks (one near-saturated) plus CP26 as a measured saturation check (median 0.998 with the text-only seed, so not evolved); one executor; 8–16 rollouts per arm; three rounds of evolution each. Seeds are labels (the API exposes no sampling seed), so arms are independent samples compared by rank test.

Rationale (the proposer's own): Measured weakness: the incumbent's adjoint template reaches ~5.75 on its first evaluation. This harness keeps the incumbent template unchanged except for an optional warm-start block. It adds a text-only custom tool, `continue_from_best`. The tool reads the best evaluated permittivity from ctx.best_state(), quantises the 60x60 design region to 6 bits (60 lines of 60 safe characters), and inserts it into the best program's RHO_INIT block. It also sets a smaller continuation LR and returns the complete ready-to-paste program. Each evaluate cycle then continues Adam from the best design instead of restarting, so roughly 10 cycles give about 10x the optimisation time. The decoder tolerates copy errors: it filters, pads and truncates, so a garbled character only perturbs one pixel. The optimiser's first iterate is the warm start itself, so results should not regress far. The best program is kept regardless. The tool shows no images, so it is a legitimate no-visual harness judged on help alone.

import re
import numpy as np

ALPH = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_"


def run(ctx, args):
    prog = ctx.get_best_program() or ""
    if 'END_RHO_INIT' not in prog:
        return ("The best program does not contain the warm-start template (no END_RHO_INIT marker). "
                "LoadSkill photonics-warmstart-template, install its program verbatim, evaluate it, then call this tool again.")
    st = ctx.best_state() or {}
    try:
        eps = np.array(st.get('epsr'), dtype=float)
    except Exception:
        return "Best state has no usable epsr yet; evaluate the template first."
    if eps.ndim != 2 or eps.shape[0] < 90 or eps.shape[1] < 90:
        return "Best state has no usable epsr yet; evaluate the template first."
    rho = np.clip((eps[30:90, 30:90] - 1.0) / 11.0, 0.0, 1.0)
    q = np.clip(np.rint(rho * 63.0).astype(int), 0, 63)
    lines = [''.join(ALPH[int(val)] for val in row) for row in q]
    block = 'RHO_INIT = """\n' + '\n'.join(lines) + '\n"""  # END_RHO_INIT'
    new, nsub = re.subn(r'RHO_INIT = """.*?"""  # END_RHO_INIT', lambda mm: block, prog, count=1, flags=re.S)
    if nsub == 0:
        return "Could not locate the RHO_INIT block in the best program; reinstall the template verbatim."
    lr = args.get('lr', 0.02)
    try:
        lr = float(lr)
    except Exception:
        lr = 0.02
    lr = min(max(lr, 0.001), 0.2)
    new = re.sub(r'(?m)^LR = .*$', lambda mm: 'LR = %g' % lr, new, count=1)
    try:
        bs = ctx.best_score()
    except Exception:
        bs = float('nan')
    head = ("Best score so far: %s. Warm start embedded from the best design (mean rho %.3f), LR=%g.\n"
            "Paste EVERYTHING below this line verbatim with edit_solution (full rewrite), then evaluate_solution.\n"
            "----- PROGRAM -----\n" % (str(bs), float(rho.mean()), lr))
    return head + new
